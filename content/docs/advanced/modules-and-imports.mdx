As your Pace project grows, you'll naturally want to split your codebase into multiple files. Pace handles this elegantly through its module system. Unlike older C/C++ style `#include` directives which simply copy-paste text, Pace's module system is fully semantic.

## The Module System

In Pace, every `.pace` file is automatically considered a module. You do not need to explicitly declare a `module name` at the top of the file; the file's path relative to your source directory determines its module identity.

By default, all declarations (classes, functions, bindings) are **public** to the module they are defined in, but **private** to the rest of the project unless explicitly imported.

## Importing Modules

To use code from another file, the standard library, or external packages, you use the `import` statement. Imports must appear at the top of the file.

```pace
// Relative import
import "./math"

// Standard library import
import std:io

// External package import
import http
```

### Selective Imports and Shadowing

To avoid polluting your namespace, you can selectively show or hide specific symbols from an imported module:

```pace
// Only imports 'print' and 'readLine'
import std:io { show print, readLine }

// Imports everything EXCEPT 'Iterable'
import std:core { hide Iterable }
```

If you declare a variable or type in your file that shares a name with an imported symbol, the local declaration will automatically **shadow** the imported symbol.

### Aliasing Imports
If a module path is too long or conflicts with a local variable, you can alias it using the `as` keyword:

```pace
import "network/http/client" as HttpClient

var response = HttpClient.get("https://pace-lang.org")
```



## Exporting

Sometimes, a module acts as a "barrel" or aggregate for a larger package. You can re-export another module's contents directly so that consumers only need to import your aggregate module.

```pace title="api.pace"
// Re-exports the entire internal endpoints module
export "internal/endpoints"
```

> [!TIP]
> Keep your dependency graphs clean! Explicit `show` imports make it instantly clear to any reader exactly which dependencies a file relies on.
